Preview options control where [`preview`](/graphics-kit-publisher/commands/#preview) publishes to.

By default, each branch gets its own subdirectory of your project's preview URL, so two people previewing at once don't overwrite each other's build:

```
https://graphics.thomsonreuters.com/testfiles/2025/ayzrxlqerve/_branches/feat-new-map/
```

The subdirectory is the branch name slugified — `feat/new-map` becomes `feat-new-map`.

Branch builds sit under a reserved `_branches/` directory rather than directly beneath the preview root. The root holds your canonical build's own top-level directories — `cdn`, `embeds`, and every top-level route — and a branch named after one of them would otherwise upload itself over those files. `world-cup-2026` is a real page on one of our projects *and* a perfectly plausible branch name.

<Aside type="note">
Nothing to do in your project. `getBasePath('preview')` returns the branch's URL while the publisher is building it, so your page builder gets the right base path on its own.

The branch part is worked out fresh on every run and is **never** written to package.json. The URL saved there stays the one URL every branch agrees on — otherwise it would be a different value on each branch, which is a standing merge conflict in the one file every branch touches.
</Aside>

## perBranch

- **Type:** `boolean`
- **Default:** `true`

Whether to give each branch its own subdirectory.

Set to `false` for the old behaviour, where every branch publishes to the same URL and the last preview to run wins.

```typescript
// publisher.config.ts
export default defineConfig({
  preview: {
    perBranch: false,
  },
});
```

An explicit `--branch <name>` still wins over `perBranch: false` — the flag exists to put one preview somewhere specific, and quietly sending it to the shared root instead would land it on top of whatever is being reviewed there. Use `--no-branch` when you do mean the root.

## rootBranches

- **Type:** `string[]`
- **Default:** `['main', 'master']`

Branches that publish to your preview URL itself rather than a subdirectory of it, so the link you've shared for the project keeps working.

Matched case-insensitively against the branch name, not its slug — write the branch as you'd type it at a terminal.

Your list replaces the default outright rather than adding to it, so this publishes only `develop` to the root, and `master` gets a subdirectory like any other branch:

```typescript
// publisher.config.ts
export default defineConfig({
  preview: {
    rootBranches: ['develop'],
  },
});
```

Set it to `[]` if no branch should publish to the root.

<Aside type="note">
A pull request's head branch never qualifies, whatever it's named. The head ref is chosen by whoever opened the pull request — and `main` is what you get by default from anyone working on a fork without branching — so honouring it would let an outside contribution publish over your canonical preview in any workflow that makes credentials available to pull requests.
</Aside>

## How the branch is worked out

In order, the publisher uses:

1. The `--branch` flag
2. `PUBLISHER_PREVIEW_BRANCH`
3. `GITHUB_HEAD_REF`, which GitHub Actions sets on a pull request
4. `GITHUB_REF_NAME`, which it sets on a push
5. `git rev-parse --abbrev-ref HEAD`
6. The short commit hash, if the checkout has no branch

The environment comes before git deliberately. `actions/checkout` leaves a detached HEAD, so git alone can't name the branch in CI — the one place branch previews matter most. And `GITHUB_HEAD_REF` comes first because on a pull request `GITHUB_REF_NAME` is the merge ref, `395/merge`, rather than the branch you'd recognise.

<Aside type="caution">
Slugs are lossy, so two branches can collide: `feat/a-b` and `feat-a-b` both give `feat-a-b` and would share a preview. Rare enough that it's worth keeping URLs readable — but if you hit it, pass `--branch` to name one of them something else.
</Aside>
